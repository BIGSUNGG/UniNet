# 0001. 하네스 엔지니어링 도입

- **상태**: 승인됨
- **날짜**: 2026-09-13
- **결정자**: 사용자 (프로젝트 소유자)

## 배경 (Context)

- 저장소 초기화 단계. 코드보다 먼저 사람-AI 협업 규칙을 확정해야 드리프트를 막을 수 있다.
- 기존 에이전트 작업은 문서가 방치되기 쉽고, 모호한 요청을 추측으로 진행하며, 요청 자체의 문제를 검토하지 않는 경우가 많다.
- 사람과 AI가 같은 문서를 계속 참조하려면 버전 관리되는 단일 진실 공급원이 필요하다.

## 결정 (Decision)

다음 네 가지 원칙을 pi 하네스로 강제한다:

1. **문서 우선** — `Document/` 폴더를 Obsidian Vault이자 SSoT로 사용. 기능 추가/수정/제거 시 항상 상세 문서화, 작업 시 필요 문서 선독. 누락 방어로 doc-guard 훅이 감시·재촉한다.
2. **능동 질문** — 정해야 하거나 애매하거나 궁금하면 반드시 질문. 추측 진행 금지.
3. **OOP/SOLID** — 모든 코드 구현에 적용. 과잉 추상화(YAGNI 위반)는 동시에 금지.
4. **요청 비판적 검토** — 사용자 요청의 잠재 문제를 리스크와 함께 제시하고, 진행 여부를 확인받는다.

추가로: 의미 있는 코드 변경은 reviewer 서브에이전트가 `CLEAN` 판정할 때까지 수정-재리뷰를 반복한다 (무제한 라운드, 정체 시 사용자 보고).

구현 수단: `AGENTS.md`(전 세션 로드) + `.pi/skills/`(doc-sync, review-until-clean) + `.pi/extensions/doc-guard.ts` + `.pi/agents/reviewer.md`.

## 결과 (Consequences)

- **긍정**: 문서-코드 불일치 조기 발견, 추측 기반 오구현 감소, 일관된 코드 품질 기준, 결정 이력 축적.
- **부담**: 세션당 문서 갱신·리뷰 루프로 토큰/시간 비용 증가. 사소한 변경에도 절차가 따름.
- **완화**: doc-sync가 변경 종류별 갱신 범위를 최소화하고, review-until-clean은 "의미 있는 변경"에만 적용한다.
- **폐기 방법**: 이 ADR을 Rejected/대체 상태로 바꾸고 관련 하네스 요소를 제거한다 (doc-sync 절차).
