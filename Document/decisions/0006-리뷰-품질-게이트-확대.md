# 0006. 리뷰 품질 게이트 확대 — 구조·보안·속도 차원화와 README 갱신 규칙

- **상태**: 승인됨
- **날짜**: 2026-09-14
- **결정자**: 사용자 (프로젝트 소유자)

## 배경 (Context)

- 기존 품질 게이트는 "의미 있는 코드 변경"만 트리거였고, 검토 기준도 정확성/SOLID/규약/문서 동기화에 집중 — 하네스(개발 환경) 변경과 보안·성능 결함이 게이트 밖에 있었다.
- UniNet은 상용 게임 서버용 네트워크 프레임워크로, 신뢰 경계(네트워크)와 hot path가 핵심 품질 영역이다. 리뷰어가 이를 일관된 기준으로 보려면 차원별 기준 문서가 필요하다.
- 라이브러리 사용자에게 기능을 알리는 창구(README)가 없는 상태에서, 기능 추가 시 문서 갱신 범위에 README가 없었다.

## 결정 (Decision)

1. **트리거 확대** — 품질 게이트를 "코드나 개발 환경이 수정되었을 때"(기능 추가/수정/제거, 리팩토링, 버그 수정, 빌드·설정 변경 등)로 확대한다. (`AGENTS.md`, `review-until-clean`, `Document/harness.md`)
2. **검토 차원 3개 명시 + 차원별 스킬 신설** — reviewer가 구조·보안·속도를 검토하며, 상세 기준은 차원별 스킬로 분리한다: `.pi/skills/review-structure/`(레이어링·SOLID·YAGNI), `.pi/skills/review-security/`(서버 권위·신뢰 경계·RPC/직렬화·DoS), `.pi/skills/review-performance/`(hot path GC·할당·잠금·복잡도).
3. **서브에이전트 1명 유지** — 차원마다 리뷰어를 분리하지 않고 기존 reviewer 1명이 3개 스킬을 참조해 검토한다 (리뷰 비용 최소화, CLEAN 루프 단일 유지).
4. **README 갱신 규칙** — 기능 추가·수정 시 `README.md`에도 반영한다. 없으면 최초 기능 변경 시 생성한다.

## 결과 (Consequences)

- **긍정**: 보안·성능 결함을 게이트 단계에서 일관되게 포착, 하네스 자체 변경도 검토 대상화, 차원 기준이 문서화되어 리뷰 편차 감소.
- **부담**: 빌드·설정 변경에도 리뷰가 따르는 비용 증가. 오타·포맷 수준은 기존대로 사용자 판단으로 생략 가능.
- **완화**: reviewer가 변경 성격에 맞는 차원 스킬만 적용(속도 지적은 측정 근거 요구)해 과잉 지적을 억제.
- **폐기 방법**: 이 ADR을 대체 상태로 바꾸고 차원 스킬 3개를 제거, reviewer 기준을 구버전으로 되돌린다.
