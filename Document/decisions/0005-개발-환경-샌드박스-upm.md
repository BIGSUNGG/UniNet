# 0005. 개발 환경 — Unity 샌드박스 + UPM 로컬 참조

- **상태**: 승인됨
- **날짜**: 2026-09-14
- **결정자**: 사용자 (프로젝트 소유자)

## 배경 (Context)

- 구현 착수 전 개발 환경 구조가 미확정이었다. 후보: ① 순수 sln 우선(netstandard2.1 csproj) / ② UnityEngine.dll 직접 참조 / ③ Unity 샌드박스 + UPM 로컬 참조.
- 이 프로젝트의 최대 기술 리스크는 "소스젠 3종(MessageProtocol·DRPC·UniNet 자체 젠)이 Unity 컴파일 파이프라인에서 동작하는가"([[plan]] 스파이크 1순위)다. ①·②는 컴파일만 되고 이 검증이 불가능하며, ②는 에디터 버전별 DLL 경로 수동 관리 부담도 있다.
- ③은 Mirror·FishNet·NGO 등 상용 유니티 라이브러리의 표준 개발 방식이다.

## 결정 (Decision)

- **③ Unity 샌드박스 + UPM 로컬 참조**로 개발한다.
- UniNet 저장소 자체를 UPM 패키지로 구성한다 (`package.json` + Runtime asmdef).
- 샌드박스는 **저장소 내 `/Sandbox`** Unity 6 프로젝트로 두고, `Packages/manifest.json`에서 `"com.ds.uninet": "file:../.."` 로컬 참조한다. (기존 DS_RPC·MessageProtocol의 in-repo Sandbox 패턴과 동일)
- sln/csproj는 Unity가 asmdef 기준으로 자동 생성한다 — 직접 작성·유지하지 않는다.
- 코어 로직 테스트는 Unity Test Framework EditMode로 시작한다. dotnet 이중 파이프라인(csproj + dotnet test)은 EditMode 루프가 실제로 느려지면 그때 재검토한다.

## 결과 (Consequences)

- **긍정**: 소스젠·IL2CPP·전용서버 빌드를 실제 Unity 파이프라인에서 상시 검증한다(플랜 리스크 제거 순서와 일치). IDE 작업은 여전히 sln로 수행한다. 업계 표준 방식.
- **부담/리스크**: Unity 재컴파일에 따른 반복 비용. 에디터 버전 고정 필요(설치본 6000.3.14f1 / 6000.5.3f1 / 6000.6.0f1 중 샌드박스 생성 시 확정).
- **완화**: 샌드박스는 언제든 재생성 가능한 폐기물로 취급(`Library/` 등 gitignore). 핵심 소스는 항상 패키지 쪽에만 둔다.
- **폐기 방법**: 개발 환경 전환(예: dotnet 이중 파이프라인 승격) 시 이 ADR을 대체하고 [[plan]]·[[architecture]]를 갱신한다.
