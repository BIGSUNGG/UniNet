# 0002. 기반 스택과 스코프 확정

- **상태**: 승인됨
- **날짜**: 2026-09-13
- **결정자**: 사용자 (프로젝트 소유자)

## 배경 (Context)

- UniNet의 정의가 확정되어야 문서·설계·구현이 정합되게 진행될 수 있다.
- 직렬화(MessageProtocol)와 RPC(DRPC) 인프라가 이미 존재하고, 재사용 여부가 아키텍처를 좌우한다.
- "언리얼 Network Framework의 모든 기능"은 범위가 크고 일부는 엔진 통합 수준이라 문서화 방식이 필요했다.

## 결정 (Decision)

1. **정체성**: UniNet은 상용 유니티 게임 서버용 네트워크 프레임워크 라이브러리. 원칙은 **"사용은 간단하게, 기능은 강력하게"**.
2. **기반 스택**: MessageProtocol(직렬화)과 DRPC(RPC)를 **적극적으로 재사용**한다. 전송은 DRPC가 위임하는 Communication(RUDP+DTLS 1.2)을 간접 의존으로 쓴다. 부족한 기능만 UniNet 자체 구현. 그 외 라이브러리는 필요 시 추가(ADR 기록).
3. **런타임**: 서버는 **Unity 서버 빌드**(MonoBehaviour가 서버에서도 동작). 서버 권위 모델. 순수 .NET 서버는 지원하지 않는다.
4. **최소 Unity 버전**: **Unity 6**.
5. **스코프 문서화**: UE 패리티 기능은 [[roadmap]]의 매트릭스로 전체 풀셋을 관리하고 단계적(P1→P4)으로 구현한다. 엔진 통합 수준 기능(예측·리와인드 등)은 동등 재현이 아닌 **상응 훅 제공**으로 명시한다.

## 결과 (Consequences)

- **긍정**: 직렬화·전송·RPC 기반을 재사용해 UniNet은 Unity 통합·리플리케이션 엔진에 집중할 수 있다. 검증된 스택으로 상용 품질 기대.
- **부담/리스크**: 하위 스택(DS_*)의 변경이 UniNet에 전파된다. Unity 6 한정으로 지원 폭이 좁아진다. 기존 스택에 없는 기능(relevancy, dormancy 등)의 자체 구현 분량이 크다.
- **완화**: 의존성 규칙을 [[architecture]]에 명시하고, 스택 수정·우회는 ADR로 관리한다. 로드맵 매트릭스로 우선순위를 투명하게 유지한다.
- **폐기 방법**: 이 ADR을 대체 상태로 바꾸고 overview·architecture·roadmap을 함께 갱신한다 (doc-sync).
