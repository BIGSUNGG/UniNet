# 0025. 접속 후 씬 로드 재등록

- **상태**: 승인됨
- **날짜**: 2026-10-08
- **결정자**: DS + pi

## 배경 (Context)

- 씬 오브젝트 등록(`RegisterAllToServer/Client`)은 `ServerAsync`·`ClientAsync` 시작 시점 **1회**만 실행됐다. 씬 로드 이벤트 훅이 없어, **접속 이후 로드되는 씬**(로비 접속 → 전투 씬 로드 흐름)의 NetworkBehaviour 는 양단 영구 미등록으로 남았다.
- 실제 사고(소비 게임 ck-darkness, 2026-10): 전투 씬의 구역·고치·낙석 오브젝트들이 `IsServer == false` 상태로 `[MulticastRpc]` 송신을 불렀고, 생성 코드가 조용히 no-op 처리하면서 **씬 귀속 연출 전부가 클라이언트에 전달되지 않는 회귀**가 발생. 이관 전에는 세션 싱글턴(접속 전 생성돼 등록됨)이 전부 중계해 문제가 없었다.
- 소비 게임의 구 우회 흔적: "버스 구독형 NetworkBehaviour — 씬 로드 후라 UniNet 슬롯 등록과 무관하다(RPC 미사용)" 주석 — 씬 오브젝트는 RPC 를 쓰지 않는 방식으로 이 제약을 회피해 왔다. 라이브러리가 이 흐름을 지원하지 않으면 씬 오브젝트는 영원히 2급 시민이다.

## 결정 (Decision)

1. **씬 로드 재등록 훅** — `UniNetDriver.Ensure()`(서버·클라 양 경로의 진입점, `HideAndDontSave` 로 씬을 건너 살아남음)에서 `SceneManager.sceneLoaded` 를 프로세스 수명 동안 1회 구독. 콜백은 `NetworkBehaviour.RegisterAllToServer()` + `RegisterAllToClient()` 를 다시 부른다(환경 존재 시에만 — 각 메서드가 null 가드). **[v0.2.2 개정]** 콜백은 등록을 즉시 실행하지 않고 `UniNetEnvironment.QueueOnMain` 로 지연한다 — 아래 «개정» 참고.
2. **멱등화 — 이미 등록된 오브젝트 스킵** — `RegisterAllToServer/Client` 가 그룹 첫 컴포넌트의 `_registeredServer/_registeredClient` 플래그로 이미 등록된 오브젝트를 건너뛴다. `InitClientSnapshot` 재실행이 라이브 상태를 초기 스냅샷으로 덮어쓰는 사고와 DontDestroyOnLoad 객체(세션 싱글턴 등)의 중복 등록을 원천 차단. 파괴 후 같은 씬이 다시 로드돼 같은 스탬프의 새 인스턴스가 생기면 플래그가 false 라 정상 등록(사전 항목 교체).
3. **반환값** — 양 메서드는 새로 등록한 오브젝트 수를 반환한다. 훅은 등록 건수가 있을 때만 로그 1줄(`[UniNet] 씬 로드 네트 등록 — {씬}: 서버 +N, 클라 +M`) — 재등록 스킵으로 같은 씬 재로드가 로그를 반복하지 않는다.
4. **언로드된 씬의 잔여 등록은 정리하지 않는다** — 서버는 드라이버의 파괴 스윕(`SweepDestroyed`)이 파괴 인스턴스를 다음 프레임에 제거하고, 씬 아이디는 씬 에셋(가이드)별 유일해 재타깃이 없다. 씬 멤버십 추적은 필요해질 때까지 만들지 않는다(YAGNI).
5. **소비 계약** — 클라가 씬을 로드하기 **전에** 서버가 그 씬 오브젝트로 RPC 를 보내면 클라 쪽 등록이 아직 없어 전달이 안 된다. 늦은 씬의 이벤트는 게임 흐름상 씬 로드 완료 보고(예: SceneReady 게이트) 이후에만 발생시키는 것 — 소비자 몫의 순서 계약.

## 결과 (Consequences)

- **긍정**: 로비 → 게임플레이 흐름에서 씬 오브젝트가 RPC·리플리케이션의 1급 시민이 된다. 소비 게임은 "씬 오브젝트는 버스 구독만" 우회를 철회하고 엔티티 몸직수신 RPC 를 씬 프랍에도 쓸 수 있다.
- **부담 / 리스크**:
  - 씬 로드 콜백마다 전 씬 오브젝트 스캔(`FindObjectsByType`) — 씬 로드는 프레임당 수 회 이하의 저빈도 이벤트라 무시 가능. 이미 등록 그룹의 스킵은 플래그 1회 읽기.
  - 잔여 등록 미정리 한계(결정 4) — 스탬프 충돌이 없다는 ADR-0023 보장에 의존.
  - 소비 순서 계약(결정 5)이 문서(SKILL.md·기능 문서)에 명시돼야 한다.
- **폐기 방법**: 씬 멤버십 추적·부분 로드 등 더 정밀한 수명 관리가 필요해지면 본 ADR 을 대체.

## 알려진 한계·후속 과제

- `CreateScene`(런타임 빈 씬 생성)은 `sceneLoaded` 를 발화하지 않는다(실측) — 훅은 **로드** 이벤트에만 묶인다. 런타임 생성 씬에 오브젝트를 옮겨 쓰는 흐름은 여전히 동적 스폰이 정답.

## 개정 (2026-10-08 저녁, v0.2.2) — 등록 지연 실행

0.2.1 의 즉시 실행 훅이 리슨서버 토폴로지에서 교착을 일으켰다(소비 게임 ck-darkness 3-EXE 자동검증, 결정적 재현).

- **사고**: 게임 흐름이 «RpcLoadScene 멀티캐스트 디스패치 → 구현부에서 `SceneManager.LoadScene`» 을 UniNet 펌프(드라이버 `Update`/`PumpMain`) 콜스택 안에서 실행하고, 로드 완료의 `sceneLoaded` 콜백이 같은 콜스택에서 즉시 `RegisterAllToServer/Client`(lock 취득·스냅샷 초기화)를 돈다. 클라이언트 2개가 로비 «전원 준비» 직후 메인 스레드 동결(Update 정지·CPU 스핀), 호스트는 SceneReady 무한 대기. v0.2.0 으로 되돌리면 같은 흐름이 완주(결정적 이분법으로 훅이 원인임을 확인).
- **결정**: 콜백은 등록 본체를 `UniNetEnvironment.QueueOnMain` 로 지연한다 — 다음 프레임 드라이버 `Update` 의 펌프 배수에서 «깨끗한 콜스택»으로 실행된다. 재진입 경로(펌프 → 디스패치 → LoadScene → sceneLoaded → 등록)가 원천 제거된다.
- **시의성 계약**: 늦은 씬 오브젝트의 등록은 이제 «씬 로드 다음 프레임» 에 완료된다 — 결정 5의 씬레디 게이트를 지키는 소비자는 체감 차이가 없다(게이트는 로드 완료 보고 후 이벤트를 흘리므로 등록보다 훨씬 뒤다).
