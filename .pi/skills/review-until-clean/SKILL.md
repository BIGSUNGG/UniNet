# 리뷰어 Clean-판정 루프 (review-until-clean)

코드 변경은 reviewer 서브에이전트의 `CLEAN` 판정 없이 완료되지 않는다.

## When to Use

- 기능 추가 / 수정 / 제거, 리팩토링, 버그 수정, 빌드·설정 변경 직후 (커밋·세션 마무리 전)
- 오타 수정·순수 포맷 변경은 제외 (사용자가 요구하면 수행)
- 문서 변경만 있는 경우에도 중요 결정·규약 변경이면 검토 권장

## Procedure

1. **변경 수집**: `git diff HEAD` + 추적되지 않은 신규 파일 목록으로 변경 범위를 정리한다.
2. **리뷰 요청**: 검토를 위해 reviewer 서브에이전트를 호출하는 이유를 사용자에게 알리고 호출 여부를 질문한 뒤, 허락한 경우에만 `subagent` 도구로 `reviewer` 에이전트(프로젝트 스코프)를 실행한다. 태스크에 포함할 것:
   - 변경 목적 (사용자 요청 요약)
   - 변경된 파일 목록과 diff (`git diff HEAD` 출력, 신규 파일은 전문 또는 요약)
   - 검토 기준: 정확성/구조/보안/속도/규약/문서 동기화(README 포함) — 차원별 상세 기준은 reviewer가 스킬(review-structure / review-security / review-performance)을 읽어 적용
3. **판정 해석**: 출력 첫 줄이 `CLEAN`이면 통과. `ISSUES`면 번호가 매겨진 이슈 목록이 온다.
4. **수정**: `[반드시]` 이슈는 모두 수정한다. `[권장]` 이슈는 수용 여부를 판단하고, 거부 시 이유를 기록한다.
5. **재검토**: 수정 후 2부터 반복한다. **라운드 제한 없음** — CLEAN이 나올 때까지 계속.
6. **정치 시 탈출**: 동일 이슈가 3라운드 이상 남아있거나, 이슈끼리 모순이거나, 리뷰어가 잘못된 전제로 지적하면 루프를 중단하고 남은 이슈·이유·권고를 사용자에게 보고해 결정을 구한다 (규칙: 추측 금지).
7. **최종 보고**: 루프 통과 시 — 라운드 수, 해결된 이슈 요약, 최종 판정을 사용자에게 보고.

## Reviewer 출력 형식 (약속)

```text
CLEAN
```

또는

```text
ISSUES
1. [반드시] <파일:줄> — <문제> — <수정 제안>
2. [권장]  <파일:줄> — <문제> — <수정 제안>
```

## Pitfalls

- reviewer는 읽기 전용이다 — 부모(메인 세션)가 직접 수정하고, reviewer는 검토만 하게 한다.
- 이슈를 "나중에" 미루지 않는다 — 남길 거면 사용자 승인 아래 기록한다.
- 리뷰 통과 후 문서 동기화(doc-sync)가 빠졌는지 마지막으로 확인한다 — doc-guard가 감시한다.
- diff가 너무 크면 reviewer에게 파일 단위로 나눠 전달하되, 판정은 전체 변경에 대해 하나로 받는다.

## Verification

- reviewer 출력 첫 줄이 `CLEAN`인가?
- 최종 보고에 라운드 수와 해결된 이슈가 포함되었는가?
