# 리뷰 차원: 보안 (review-security)

reviewer 서브에이전트가 코드 변경의 **보안 건전성**을 검토할 때 적용하는 기준. UniNet은 서버 권위(authoritative) 상용 게임 서버 프레임워크다 — 네트워크 반대편은 항상 적대적이라 가정한다. 판정 형식(ISSUES/CLEAN)은 reviewer 에이전트 계약을 따른다.

## When to Use

- RPC 핸들러, 메시지 직렬화/역직렬화, 상태 Replicate 경로 변경
- 클라이언트 입력·패킷을 받아 처리하는 코드 변경
- 인증·권한·연결 수명주기 관련 변경

## Checklist

1. **서버 권위 위반** — 클라이언트가 보낸 상태·결정을 서버가 검증 없이 수용하는가? (위치, 입력 결과, 자원 소모 등). 서버가 판단해야 할 로직이 클라이언트에 누출됐는지.
2. **RPC 입력 검증·인가** — 호출자 권한 확인, 대상(target) 유효성, 인자 범위/타입 검증이 핸들러 진입점에 있는가?
3. **직렬화/역직렬화 안전성** — MessageProtocol/DRPC 경계에서 페이로드 크기 상한, 필드 수/깊이 제한, 알 수 없는 타입·버전 처리, 예외가 연결·서버를 죽이지 않는지.
4. **리소스 소진 (DoS)** — 패킷당 무제한 할당, 검증 전 대형 버퍼 할당, 무제한 큐·컬렉션 성장, 초당 요청 한도 부재.
5. **메모리 안전** — `unsafe`·포인터·고정 버퍼 사용 시 경계 검사, 인덱스 검증, 관리되지 않는 메모리 해제 보장.
6. **비밀·민감정보** — 키/토큰 하드코딩, 로그·예외 메시지에 플레이어 개인정보나 내부 정보 노출.
7. **신뢰 경계 명시** — 네트워크에서 온 모든 데이터가 검증 게이트를 통과하는가? 경계를 새로 만들거나 우회하는 경로가 생겼는지?

## Pitfalls

- 보안 이슈는 대부분 `[반드시]` — 신뢰 경계에서의 검증 누락은 "나중에 추가"로 넘기지 않는다.
- 성능 근거로 검증 생략을 정당화하지 못하게 한다 — 둘 다 필요하면 둘 다 요구.
- 실제 공격 시나리오를 한 문장으로 쓴다 — "위험해 보임"만으로는 지적하지 않는다.

## Verification

- 모든 보안 이슈가 공격 시나리오(누가, 무엇을 보내면, 무슨 일이 일어나는가)를 갖는가?
- 변경된 코드가 신뢰 경계를 통과하는 데이터를 새로 다루는가 — 다룬다면 검증 위치를 확인했는가?
