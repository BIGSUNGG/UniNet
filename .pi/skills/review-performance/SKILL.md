# 리뷰 차원: 속도 (review-performance)

reviewer 서브에이전트가 코드 변경의 **런타임 성능 영향**을 검토할 때 적용하는 기준. UniNet은 Unity 6 기반 게임 서버·클라이언트 공용 프레임워크다 — 서버는 처리량, 클라이언트는 프레임 예산이 병목이다. 판정 형식(ISSUES/CLEAN)은 reviewer 에이전트 계약을 따른다.

## When to Use

- 네트워크 송수신, 직렬화, Replicate 같은 hot path 변경
- 컬렉션·버퍼·풀링 구조 변경, 스레딩·잠금 변경
- 매 프레임/틱 호출되는 경로(Update 루프, 서버 티커) 변경

## Checklist

1. **GC 압력 (hot path)** — 매 프레임·패킷마다 실행되는 경로의 할당: 문자열 연결/보간, 값 타입 boxing, LINQ·`foreach` 헬퍼 열거자, 람다·클로저 캡처, 배열 재할당.
2. **버퍼·풀링** — 재사용 가능한 버퍼를 매번 새로 할당하는가? 풀이 있다면 풀을 우회하는가? 반환 누수는 없는가?
3. **불필요한 복사** — 큰 컬렉션·바이트 배열의 방어적 복사, 값 타입 대형 구조체의 암묵 복사, `IEnumerable` 중간 컬렉션.
4. **잠금·동시성** — 잠금 범위 과다(전역 락에서 세부 락으로 좁힐 수 있는가), 잠금 안에서의 I/O·콜백·무거운 연산, 이중 검사 부재.
5. **알고리즘 복잡도** — hot path의 O(n²) 이상 탐색, 매번 전체 스캔으로 답하는 구조(인덱스·딕셔너리로 바꿀 수 있는지).
6. **동기 블로킹** — 프레임 루프·서버 틱에서 동기 I/O, `Thread.Sleep`, 블로킹 대기.
7. **Unity 특이사항** — 반복 `GetComponent`, 문자열 기반 `GameObject.Find` 등 프레임 예산을 까는 API를 루프 안에서 호출하는지.

## Pitfalls

- 측정 근거 없는 최적화 요구 금지 — "느릴 것 같다"는 지적이 아니라, hot path 여부와 할당·복사량이라는 **검증 가능한 근거**를 제시한다. 확신 없으면 `[권장]` + "확인 필요".
- cold path(초기화, 설정, 드문 이벤트)의 미시 최적화는 지적하지 않는다 — 가독성 해가 더 크다.
- 보안 검증을 성능 이유로 빼는 코드는 보안 차원으로 지적(성능 정당화 불인정).

## Verification

- 각 성능 이슈가 hot path 근거(호출 빈도·경로)를 명시하는가?
- 제안한 수정이 기능·안전성을 해치지 않는다고 확인했는가?
